## 증상: 멀쩡한 데이터가 통째로 "미지원"

메타데이터 관리 플랫폼에서 특정 프로젝트만 산출물(정의서)이 통째로 **"미지원"** 으로 떴다. 물리 테이블 정의서, 논리 테이블 정의서, 팩트·디멘전까지 전부. 그런데 같은 프로젝트를 모델 편집 화면에서 열면 데이터가 멀쩡히 보인다. 데이터가 없는 게 아니라, **산출물 쪽에서만 못 찾는** 것이다.

## 원인: 데이터가 "세대 포인터" 너머에 있었다

이 모델 메타는 버전마다 행을 통째로 복제하지 않는다. 대신 각 버전 행이 **실제 데이터가 저장된 세대(generation)를 가리키는 포인터**(`meta_dv_id`)를 갖는다.

핵심은 편집 방식이었다. 시트/컬럼을 조금 고쳐 저장하면, append-only로 **새 버전 행**이 하나 생긴다. 그런데 이 증분 편집은 데이터를 새 버전 id로 복제하지 않는다. 새 행의 포인터를 **이전 세대**로 걸어두고, 그 세대의 행을 제자리에서 수정할 뿐이다.

```
최신 버전(dv2424)  ──meta_dv_id──▶  종단 세대(dv2284)  ← 실데이터 255행
       │
       └─ 이 id로 조회하면? → 0행
```

그래서 `WHERE data_version_id = 최신버전id` 로 조회하면 **0행**이 나온다. 데이터는 포인터가 가리키는 세대에 살아있는데 말이다.

모델 조회/편집 경로는 전부 이 포인터를 따라가는 해석 함수(`resolveMetaKey`)를 거치고 있었다. **딱 하나, 산출물 경로만 그 해석을 빼먹고** 최신 버전 id를 날것으로 조회하고 있었다. 그래서 "마지막 작업이 편집이었던" 프로젝트만 골라서 미지원으로 떴던 것이다. 전체 재파싱으로 끝난 프로젝트는 최신 id에 데이터가 있으니 멀쩡했고.

## 진짜 교훈: 두 id의 의미가 다른데 타입이 같았다

여기서 멈추고 "산출물 경로에도 `resolveMetaKey`를 넣자"로 끝낼 수도 있었다. 하지만 이건 **두 번째로** 이 해석을 까먹은 경로였다. 세 번째, 네 번째 경로가 나오지 말라는 법이 없다.

근본 문제는 이거다. 시스템에는 의미가 완전히 다른 두 개의 id가 있는데, 둘 다 그냥 `Long` 이었다.

- **버전 정체성 id** — 사용자에게 보이는 버전, 그리고 편집 저장의 base
- **물리 메타 세대 key** — 실제 데이터가 저장된 위치

이름도 타입도 구분이 없으니, 새 코드를 짜는 사람은 "여기 어떤 id를 넣어야 하지?"를 매번 기억에 의존해 결정해야 한다. 기억은 언젠가 실패한다. 그게 이 버그였다.

그래서 두 값을 담는 작은 타입을 만들고, 접근자 이름을 아예 갈라놨다.

```java
record ResolvedModelVersion(
    Long latestDvIdForSaveBase,  // 편집 저장 base — 원본 최신 id
    Long metaReadKey,            // 데이터 읽기 — 세대 해석된 key
    ...
) {}
```

`latestDvIdForSaveBase()` 를 읽기 쿼리에 쓰거나, `metaReadKey()` 를 편집 저장 base로 쓰면 이제 코드를 읽을 때 바로 어색하다. 오용이 **눈에 띈다**. 이게 타입 경계의 힘이다. 주석으로 "여기엔 raw id를 넣으세요"라고 적는 것보다, 애초에 잘못 넣기 어렵게 만드는 게 낫다.

## 곁다리로 배운 것들

- **부작용 없는 해석 함수를 따로 뒀다.** 기존 해석 함수는 포인터가 없으면 무거운 재파싱(쓰기 트랜잭션)을 트리거할 수 있었다. 산출물 목록은 자주 열리는 가벼운 조회인데, 거기서 재파싱이 터지면 조회가 수리 작업으로 돌변한다. 그래서 "포인터만 따라가고 절대 재파싱 안 하는" 얇은 함수를 별도로 만들었다.
- **잘못된 방향의 실패가 더 안전하다.** 편집 저장 base에 실수로 읽기 key가 들어가면, 조용히 틀린 데이터가 저장되는 게 아니라 명시적으로 "base 불일치" 에러가 난다(원래 그렇게 설계돼 있었다). 조용한 손상보다 시끄러운 실패가 백 배 낫다.
- **회귀 테스트는 버그를 실제로 재현해야 한다.** 이 버그는 "편집 저장 경로"를 타야만 재현되는데, 테스트 환경에서 그 경로가 다른 분기로 빠지면 버그가 없는데도 초록불이 뜬다(false-green). 그래서 테스트에서 포인터 상태를 직접 심어 `최신id ≠ 세대key` 를 결정론적으로 만들었다.

## 마무리

"읽기 경로가 세대 해석을 까먹었다"는 증상이지, 병이 아니다. 병은 "의미가 다른 두 값에 타입 경계가 없다"는 것이었다. 증상만 고치면 다음 사람이 또 밟는다. 타입으로 갈라두면, 다음 사람이 밟기 전에 컴파일러가 먼저 멈칫하게 만든다.
